# Case Study：IP 群高光

> 一个关于「如何让一个微信群的优质内容不再被刷走」的产品实践记录。

---

## 项目背景

我在一个 IP 创作者社群里待了一年多。这个群的内容密度其实很高：群主经常输出干货观点，群友会分享自己的作品和实验结果，遇到具体问题时也总有人给出靠谱的答案。

但这些内容的命运几乎一致——发出来的当天被点赞、被回复，第二天就沉到几百楼之下，再也没人翻得到。我自己也试过手动整理「本周精华」发到群里，但每次都卡在同一个环节：**整理太耗时，坚持不下来**。

这个项目的起点很朴素：我想知道，如果把「整理」这件事变成一个轻量的、每周可重复的工作流，会发生什么。

## 问题发现

第一次尝试手动整理时，我犯了一个典型的错误：把一周的聊天记录从头读到尾，试图「总结」。结果产出像一份会议纪要——面面俱到，但没有任何一句话让人想转发。

复盘之后我发现真正的问题不是「信息没被记录」，而是**判断没有被做出来**。聊天记录里的信息密度其实是均匀的（每条消息看起来都差不多），但**价值密度是极不均匀的**——99% 是闲聊和噪音，1% 是「这条消息让好几个人忍不住回复」的瞬间。

「总结全部」恰恰抹平了这种不均匀，把噪音和黄金按相同权重平铺开来。这是为什么我整理的「精华」读起来像周报，而不像「精华」。

## 为什么不是普通群精华

市面上能想到的「群聊总结」工具，逻辑基本都是：抓取聊天记录 → AI 摘要 → 输出一份文字稿。这类工具解决的是「我没时间看完群消息，给我个 tl;dr」。

「IP 群高光」要解决的是另一个问题：**这个群本来就有创作能力，只是创作的产出散落在聊天记录里、没有被「收集」起来**。所以这个产品的核心动作不是「摘要」，而是「策展」——

- 摘要的输入是「全部内容」，输出是「内容的压缩版」。
- 策展的输入是「全部内容」，输出是「被挑出来、被重新包装的一部分内容」，挑选本身就是价值判断，包装本身就是二次创作。

这个区别决定了整个产品的形态：不是做一个「自动总结机」，而是做一套「内容筛选 + 多形态改写 + 长期归档」的编辑工作流，AI 在其中扮演的角色更像「主编的执行助手」，而不是「速记员」。

## 产品定位

**把微信群里最能激活大家的内容，转化为作品样本、行动清单、社群记忆和长期知识资产。**

定位的关键词是「激活」——判断一条内容是否值得处理，看的是它在群里**引发了什么反应**，而不是它本身写得多么完整。一句话引发了十条追问，比一段完整但无人回应的长文更值得被剪辑出来。

围绕这个定位，产品识别三类「高光事件」：

1. **群主观点高光**——一个判断/方法被群成员认同或追问
2. **群友作品高光**——一份作品被分享并获得关注，反哺创作者的成就感
3. **话题讨论高光**——一场讨论引发多人接力，留下值得继续追问的问题

## 用户与场景

- **核心用户：群主自己**。场景是每周固定花 1-2 小时，把零散记录的素材跑一遍工作流，产出本周的三个发布版本。
- **次要用户：社群运营者**。如果这套工作流跑通，可以复用到其他付费/兴趣社群，作为「证明这个群很活跃、很有价值」的运营证据。
- **间接用户：被剪辑的群友**。他们不直接使用这个产品，但是产品最重要的「反馈对象」——被认真对待的体验本身会反向激励他们更认真地参与和分享。

## MVP 范围

**做的事：**
- 一个标准化的素材输入模板（`inbox/`），方便随手粘贴聊天内容
- 六个加工步骤的 prompt（筛选 → 周刊 → 微信短版 → 飞书版 → 知识沉淀 → 下周计划）
- 六个长期知识库（话题 / 方法论 / 成员问题 / 案例 / 金句 / 下周选题），按周累积
- 一个静态展示页（`demo.html`），作为产品本身的「样品」

**明确不做的事：**
- 不做 OCR：聊天截图需要自己誊写成文字
- 不接飞书 API：飞书版是 Markdown，手动复制粘贴
- 不爬微信：素材完全靠人工粘贴
- 不做数据库：所有状态都是 Markdown 文件，对人和对 AI 都是「可读的源代码」

这个边界不是「能力不够所以先不做」，而是**刻意的**：在验证「策展逻辑是否成立」之前，任何自动化都是在给一个尚未验证的假设上加固，成本收不回来。MVP 的目标是验证「每周筛选 + 改写」这件事是否真的能产生第三档（优秀）甚至第四档（惊艳）的效果——这个验证不需要任何工程投入，只需要纪律性地跑完工作流。

## AI 工作流

每周一个循环，七个步骤：

```
inbox（素材）
  -> 01-extract（A/B/C 分级筛选）
  -> 02-weekly-digest（正式周刊）
  -> 03-wechat-short（微信群短版）
  -> 04-feishu-version（飞书归档版）
  -> 05-archive-knowledge（六库沉淀）
  -> 06-next-week-plan（下周运营计划）
```

每一步都是「素材/上一步产出 + 一个明确的 prompt」喂给 AI，产出一个 Markdown 文件。整个链路里**没有一步是端到端自动化的**——这是有意为之：每一步的产出都需要人工核对（尤其是「关键观点必须能回到原始聊天材料」这条硬约束），AI 负责的是「按照编辑标准把素材加工成稿」，最终把关始终在人。

## 三方分工：用户 / GPT-Codex / Claude Code

这个项目本身的搭建过程，也是一次「人 + 多个 AI 协作」的实践：

- **用户**：负责产品判断——决定要不要做这个项目、定位是什么、MVP 边界画在哪里、四档质量标准如何定义、最终对每期产出的发布把关。这部分判断不能外包，是整个项目唯一不可替代的部分。
- **GPT-Codex**：在工作流的「内容生成」环节里，承担按 prompt 产出周刊/短版/归档内容的执行工作——给定明确的输入和编辑标准，输出符合格式的初稿。
- **Claude Code**：负责项目的工程化搭建——设计目录结构、撰写六个 prompt 的编辑标准、构建知识库的字段格式、搭建静态展示页 `demo.html`，把「一个想法」变成「一套可以每周重复运行的系统」。

这个分工的本质是：**判断力是人的，文字生成是 AI 的执行层，系统结构是 AI 的工程层**——三者分开，是因为它们需要的能力和反馈周期完全不同，混在一起反而会互相拖慢。

## 第一周验证方式

第一周不追求「完美的一期」，追求的是**跑通一次完整循环并拿到真实反馈**：

1. 随手记录素材，不打磨格式，先求「有」
2. 跑完七个步骤，产出 Vol.001
3. 把微信短版发到群里，**观察而不是猜测**：
   - 被 @ 的人有没有回复？
   - 「下周值得继续聊什么」里的问题有没有人接？
   - 有没有人主动转发飞书版？
4. 把这些观察记录下来，作为下一期筛选标准的校准依据

第一周的「成功」不是「这期周刊写得好不好」，而是「**这个循环是否产生了能指导下一期的真实信号**」。

## 成功指标

按 `quality-bar.md` 的四档划分，分阶段看：

| 阶段 | 指标 |
|---|---|
| 第 1-2 期 | 能跑通全部七步，产出结构完整（合格版本） |
| 第 3-4 期 | 「成员高光」点名后有人回复，「下周话题」有人接话（优秀版本） |
| 第 5-8 期 | 群友开始主动提及「这个能不能写进周刊」；`knowledge/` 里出现可识别的、跨周复现的话题/方法（向惊艳版本靠近） |
| 长期 | 整个项目（工作流 + 样本 + case study）可以独立作为「内容产品设计能力」的作品集证据对外展示 |

终极指标始终是 `quality-bar.md` 里的那句话：**这份东西有没有让一个普通微信群，突然显得像一个正在共同创作的社区？**

## 后续路线

按四个方向逐步推进，每个方向只有在前一个方向被验证后才启动：

### 1. 外显化（Externalize）

把目前「只有群主自己看得到」的产出，变成群友可见、可参与的形态——比如把 `demo.html` 升级成一个可以分享给群外人的「这个群在做什么」的公开页面，让「被收录」本身成为一种群内的可见认可。

### 2. 专门化（Specialize）

目前的 prompt 是通用的「IP 创作者群」模板。如果跑通了，下一步是针对不同类型的社群（技术群、读书会、商业社群）调整筛选标准和栏目结构——比如技术群可能更需要「踩坑记录」而不是「成员高光」。

### 3. 自动化（Automate）

在策展逻辑被验证之后，逐步把「人工粘贴素材」替换为更轻量的输入方式（比如群内打了某个标记的消息自动收集），但**筛选和改写环节保留 AI + 人工复核**，自动化的是「输入」，不是「判断」。

### 4. 复利化（Compound）

`knowledge/` 六个库是这个产品最长期的资产。当积累到一定周数后，可以反向生产新内容——比如「这个群三个月内提到最多的方法论」「成员问题库里还有哪些悬而未决的问题，适合做一期专题」。这一步是 GitHub Octoverse 式的「趋势沉淀」真正开始发挥作用的阶段：单期内容是流量，长期积累的知识库才是这个社群真正的护城河。
